# 逆向工作流

## 何时使用

只要结论依赖以下任一证据，就走本工作流：已发布的可执行文件与安装包、反编译/反汇编产物、运行中的应用行为、抓包与内存观察。

如果目标有完整源码仓库且问题能靠读源码回答，不要走本工作流。

## 授权边界

先确认目标归属。仅分析用户自己拥有、或用户明确声明已获授权的软件。用户未说明时，用一句提问确认，不要自行假设；确认后继续，不要反复追问。

## 五步流程

1. **定问题**：把"我想知道 X"改写成可被证据判定真假的句子。例如"该功能在客户端叫什么、由哪段代码触发、是否依赖服务端返回"。
2. **判形态**：按目标形态选证据平面，不要一上手就反汇编。
   - 原生二进制 / 动态库 / App bundle → 反汇编与反编译
   - `.asar`、打包后的 JS、Electron 应用 → JavaScript 静态分析，必要时再上运行时
   - `.dll` / .NET 托管程序集 → 托管程序集分析
   - APK / IPA / MSIX / DMG / 压缩包 / 固件镜像 → 先做制品结构与解包
   - 用户本机已打开的浏览器页或 Electron 运行时 → 运行时观察
3. **取证据**：每条判断都落到具体证据上——函数地址或名称、文件偏移、字符串、调用关系、运行日志。没有落点的判断不要写成结论。
4. **收敛**：区分三类陈述并在输出里标明——**已验证**（来自工具返回的原始证据）、**推断**（由已验证事实推出，写明推理链）、**未知**（现有证据不足，写明还缺什么证据才能判定）。
5. **可重建**：交付的目标是让读者能据此重建行为，因此要给关键路径、关键参数、边界条件与未覆盖部分。

## 反模式

- 把反编译器的伪代码当成源码事实：伪代码是重建结果，变量名与类型多为推断，需交叉验证。
- 只给工具输出不给结论，或只给结论不给证据落点。
- 用文件名、字符串或图标推断功能，却不反查调用点。
- 修改目标文件后再分析却不留备份；对用户的目标文件做任何写操作前先复制一份。
- 把一次运行观察到的行为当成全部行为：先确定输入域，再下"总是/从不"这类判断。

## 上下文管理

逆向工具输出通常很大。优先把完整输出落盘到工作目录，再按需读取片段；只把结论与关键片段带回上下文。需要并行覆盖多个证据平面时，用子代理分别取证，再由主代理汇总，避免单条上下文被原始 dump 淹没。

## 工具

具体工具与调用方式由当前 composition 挂载的 REA MCP 工具提供（模型侧名称为 `mcp__rea__*`）。先用只读工具建立地图，再决定是否使用会改动目标状态的操作。
